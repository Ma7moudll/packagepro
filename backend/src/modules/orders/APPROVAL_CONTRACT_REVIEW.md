# Offline approval candidate, not released

This additive migration and code are an unpublished review candidate. Existing requests, files and orders are not assumed absent. No legacy approval is backfilled or trusted. This is not manufacturing certification.

An admin must select a print file and explicitly select a dieline or null. New saves and upload associations stamp the server-derived saved-content hash. Legacy or stale files require a fresh upload/association against the saved design, not an inferred newest file. Pending approvals bind selected input bytes, a server-owned frozen copy, an exact generated proof, saved design JSON and a versioned content hash. Camera/UI-only root fields are excluded; unknown authored fields are included. Unknown nested display fields can conservatively stale a request.

The same active request is returned without another email. Renewal is explicit and supersedes the old pending generation. Generation failures are durable and can be explicitly renewed. A provider timeout or crash after entering sending is uncertain, never an automatic resend. A crash before token finalization produces no usable emailed capability. A crash after finalization but before send requires explicit renewal; the raw token is not recoverable. Sending status can remain after a process crash and must be treated as uncertain. No live email provider was used for candidate testing.

Legacy reminder URLs and automatic cancellation jobs do not carry request identity. They are not reactivated by this candidate. Scheduling and automated expiry communications are deferred. Token expiry is enforced at approval.

Save content and file metadata now commit together; Redis mirrors after commit. Failed staged uploads/proof generation can leave unreferenced local/S3 objects. Automatic orphan cleanup is not implemented here. Export rows are type export, not eligible print/dieline inputs. Artwork review rows remain separate and cannot become production inputs. Session rebinding is guarded to owner-matching unlinked DRAFT designs. Save uses a design row lock; approval/finalization and PO creation use order then design locks. No general claim of race safety beyond tested paths is made.

PO creation, resume and PDF generation must consume the approved frozen print/dieline, recheck bytes and refuse legacy/unbound or changed state. Multiple different design IDs in one order are refused, rather than pretending one approval covers them. No first/newest-file selection is used in approval or PO consumers.

## Selected reopening policy

An explicit admin action may return awaiting_approval or ready_for_routing to pending_review before any purchase order exists. Any PO row, including incomplete rows, prevents reopening. Reopening locks the order like PO creation, supersedes prior generating/pending/approved requests, consumes unused tokens, clears current approval metadata and records a reason. It sends no email. Fresh review requires explicit input selection and renewal acknowledgement; stale file associations still require a fresh upload/attachment. Customer pages explain that only an admin can reopen before a PO and do not offer a nonfunctional send-for-revision action. No customer request is silently treated as an admin transition.
