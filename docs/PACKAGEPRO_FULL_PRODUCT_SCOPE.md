## 1. Executive summary

PackagePro is a real, test-backed packaging platform core — not a mockup. The backend (Fastify + Prisma + PostgreSQL) has **32 models, 25 registered route modules, 5 BullMQ workers, and exactly two implemented integrations: Stripe and DHL** (implemented and webhook-verified at the **code level**; this document presents no evidence of live Production credentials, funded merchant accounts, signed carrier contracts, or operational liveness — see §2.3). The frontend (Next.js App Router) has **75 pages, 20 typed API clients, 120 passing unit tests (re-verified 2026-11-15), and 16 Playwright e2e spec files**. The differentiating "packaging platform" layers are genuinely implemented and verified by tests: catalog configurator, instant pricing engine, a 2D/3D editor with a real dieline geometry engine, preflight/prepress validation with proof generation, order lifecycle with production approval, PO generation with multi-vendor grouping, vendor handshakes, production QA samples, settlements-on-delivery, invoicing, and admin/analytics.

What PackagePro is **not** yet is a commercially usable **Egyptian** packaging platform. Payments are Stripe-only with a `currency` default of `"USD"`; logistics are DHL-only; there is **zero** Arabic/RTL support; there is no vendor self-service onboarding/verification, no custom quote (RFQ) flow (proposed deferral from the initial launch — `PROPOSED — pending owner confirmation` — §7), no warehousing/inventory, no partner APIs, no subscriptions, no COD, no ETA e-invoice fields, and the `Shipment` model structurally permits **only one shipment per order** (`orderId @unique`).

The gap to the target concentrates in six clusters:

1. **Egypt payment rails** — Paymob/Fawry/wallets: zero code (frontend `lib/payment.ts` is a client-side mock).
2. **Egyptian logistics** — Bosta/Mylerz: zero code; requires the carrier abstraction first (plan OPS-06).
3. **Arabic/RTL localization** — 0 files with `dir="rtl"`, no i18n framework; spec-023 is doc-only.
4. **Supplier-side platform** — no vendor self-service onboarding/KYC; and the manufacturer portal's product pages call `/products` endpoints that **do not exist in the backend** (broken wiring). Vendor operations are decomposed into three separately classified scopes in §3 D1/D3, §7, and §8.
5. **Fulfillment** — warehousing/inventory/stock reservations: zero backend code; multi-shipment blocked by schema.
6. **Commercial services** — custom quote requests, expert support, sustainability data, partner APIs: zero backend code (docs-only specs exist for some). Custom quotes/RFQ are additionally **proposed for deferral from the initial launch — `PROPOSED — pending owner confirmation`** (§7) — the initial launch is the end-buyer marketplace, not the RFQ workflow.

Roadmap headline: a **Wave 0** of financial-correctness and integration-seam work (mostly already mandated by `docs/MASTER_EXECUTION_PLAN.md`: FIN-01…05, OPS-06, UI-01…03) plus a **recommended** MVP of **six** feature workstreams (catalog search & filters and the RFQ loop are **proposed** to move out of the MVP by two deferrals **pending owner approval** — the six-item figure is the base roadmap recommendation; the effective MVP size is conditional: **six items if both deferrals are approved, seven if exactly one is approved, eight if neither is** — until its respective approval each deferred feature remains an MVP-scope candidate — §7) precedes a commercially usable Egyptian launch. Warehousing, the partner ecosystem, subscriptions, the marketplace, and the food-packaging vertical can all be **postponed without blocking first launch**. The existing architecture (Fastify modular monolith + Next.js App Router + BullMQ + PostgreSQL) is sound for this roadmap; **no microservices transition or stack rewrite is warranted by the evidence**.

**Launch target vs long-term vision.** The intended initial commercial launch is an **end-buyer marketplace**: customers browse packaging products, configure them, place orders, and pay directly — the verified catalog → configurator → cart → checkout → payment path is the launch path (RFQ is not on it; §7). The complete long-term platform vision (RFQ/custom quotation, expert services, B2B/wholesale flows, warehousing, partner ecosystem, subscriptions, the food vertical) is larger than the initial launch and is sequenced in §7's post-MVP tiers. **No claim is made that every Packhelp-like capability is implemented**; §3's per-feature classifications are the authority.

(2) **`POST /checkout`** (`checkout.service.ts:78-94`) — order-first: creates the PaymentIntent **inline** and returns `clientSecret`. **The live frontend path is (2)**: `StripePayment.tsx` submits via `checkoutApi` `POST /checkout`, then calls `stripe.confirmPayment` with the returned `clientSecret`. The standalone path (1) plus `POST /api/payments/confirm` (`{paymentIntentId}`) are implemented but **currently have no frontend callers** (`paymentsApi.createIntent`/`confirm` in `frontend/lib/api/payments.ts` are unreferenced — grep across `app/`, `components/`, `lib/` = none). `POST /api/webhooks/stripe` (raw-body, 2 MB) is the Stripe callback.

**Existing vs proposed (clearly separated):** today there is **no shared provider abstraction** — the two creation paths are independent code paths, Stripe-only, with **no provider-selection mechanism** (verified: no `provider` concept exists in either contract). Everything from the shared service down to the target sequence below is **PROPOSED architecture, not existing implementation**.

- **Proposed consolidation (recommended): one coherent provider-selection and PaymentIntent-creation contract.** Introduce **one internal payment-provider service/adapter** (Stripe first — the existing integration logic becomes its first adapter; **Paymob is the first proposed Egyptian provider**, Fawry second) and route **both existing HTTP entry points** through it — `POST /checkout` (the live path) **and** `POST /api/payments/create-intent`. Extending `/payments/create-intent` alone would **not** integrate Paymob into the live checkout flow, because the frontend does not call it. **No duplicate payment-intent endpoint is proposed** — a separate `POST /api/payments/intent` is deliberately NOT proposed, because it would duplicate the already-registered `/payments/create-intent` route and fragment the amount/ownership contract.
- **Provider selection (proposed):** the live checkout request **passes an explicit optional `provider` field** (default `stripe`) or the server resolves the provider from the order's market/currency; **the selection is validated server-side** against the providers enabled for that currency/market (the proposed `GET /api/payments/methods` below feeds the same enablement configuration). The client's choice is never trusted beyond this validation.
- **Server-authoritative money (hard requirement, preserved from the existing behavior):** amount and currency are taken from the stored order server-side — never from the client payload; currency policy per FIN-02.
- `POST /checkout` contract extension (**proposed**): optional explicit `provider` field (default `stripe`), validated server-side per the above; existing amount/ownership behavior preserved.
- `POST /api/payments/paymob/webhook` — signature-verified Paymob callbacks (**separate URL by provider necessity**: per-provider callback endpoints + signature schemes)
- `POST /api/payments/fawry/webhook` — signature-verified Fawry callbacks
- `GET /api/payments/methods` — methods enabled for the order's currency/market
- **Security requirement (non-negotiable):** every provider webhook must meet the SEC-03b/c standard — verify authenticity server-side and re-verify state against the provider's API (mirroring SEC-03a's DHL Track re-verification), ledger-backed idempotency via a generalized `ProcessedProviderEvent`. Never trust provider JSON payloads directly.

#### Proposed target checkout-payment sequence (design requirements — NOT the current implementation)

> The current implementation is a single-step flow: `POST /checkout` creates the order and the PaymentIntent together and the frontend confirms with the returned `clientSecret`. The sequence below is the **proposed target flow** (the FIN-03/FIN-04 corrections); state names and transitions are **design requirements** — repository evidence establishes **no final state machine today**, so none is invented here.

1. Create a **draft checkout session / draft order** (proposed draft state — not producible, not presented to the customer as a placed order).
2. Calculate **authoritative order totals on the server** (FIN-01 contract).
3. Create the PaymentIntent **for the server-validated selected provider** (shared provider service — above).
4. Return the client secret (or provider equivalent) to the frontend.
5. **Mount the payment UI** (Payment Element / provider equivalent) only after the intent exists.
6. Customer **confirms payment**.
7. **Verify the payment outcome server-side** (provider webhook + state re-verification) — **client-side success is never authoritative**.
8. Transition the order into the appropriate **paid/confirmed state** (proposed state names/transitions — design requirements to be finalized in the implementation design; no state machine exists in evidence today).
9. **Clear the cart only after the required successful payment confirmation** (FIN-04) — under the default prepaid policy, production release additionally requires server-verified capture (§9 production-release rule).

- **Abandoned/failed sessions (proposed handling, to be designed):** draft orders that never reach confirmed payment **expire or are cancelled** (proposed expiry rule) without producing inconsistent orders; **retry reuses the existing PaymentIntent** where the provider allows (the existing per-order single-`Payment`-row + intent-reuse mechanism, §3 E1), so failed attempts never create duplicate payment records; a replacement intent may be created only by the server under the same ownership rules.
- **Unpaid orders:** under the **default prepaid policy**, an order that has not reached server-verified payment confirmation must not enter production; conditional COD/deposit exceptions apply only under an owner-approved policy (§9 production-release rule, §10 decision #2).

InstaPay and Vodafone Cash only as controlled pilots with verified settlement proof — never screenshots. **Production-release rule:** by default (prepaid), an order may not enter production until payment is verified server-side as captured; this rule is **conditional on the approved payment method** — phone-confirmed COD (only if approved) releases production per the designed phone-confirmation verification (**phone confirmation is not equivalent to payment capture** — the balance remains uncollected), deposit-paid (only if approved) per the designed deposit-verification rules, and any owner-approved hybrid per its designed authorization/confirmation requirements; **any approved COD/deposit exception requires a formally designed payment/order state machine, PO-release rules, reconciliation, cancellation, and RMA handling before implementation** (§10 decision #2). COD remains **decision-gated** — nothing is approved here. Gate: AC #3 and #4.

**Logistics.** Implement the OPS-06 carrier abstraction, then contract and integrate one Egyptian carrier (Bosta or Mylerz — owner decision based on negotiated rates/coverage) alongside DHL for international/express; **carrier commercial contracts require the established legal entity (§10 decision #11)**. Multi-shipment follows **Gate G-SHIP**: under Branch A — the recommended initial launch option (awaiting owner approval) — **at most one shipment record per order (schema-enforced)** with **exactly one shipment created when the order reaches the shipping stage**: an order cannot be marked shipped or delivered without its shipment record **and** verified carrier status; settlements stay per-order; **one shipment record does not imply one physical package** (consolidated multi-package handling under a single shipment must be confirmed with the selected carrier before reliance — not verified in repository evidence); order-splitting is not a platform capability and any out-of-band workaround needs explicit approval — §7; under Branch B the schema change lands jointly with the SEC track, settlements become per-shipment, **and the minimum operational workflow for creating, tracking, and settling multiple shipments is built before launch** (advanced call-off/warehouse workflows stay post-MVP unless independently required). COD remains decision-gated (E5, §10 decision #2 — the owner selects a policy: none at launch / phone-confirmation gate before PO release / deposit + balance on delivery / an owner-defined hybrid; each option changes payment state, order state, PO release, production start, carrier COD collection, settlement/reconciliation, and cancellation/RMA) with a payment-state and reconciliation design as its precondition. Gate: AC #5, plus AC #6 (Branch B) or the Branch A criteria (§7).

**Language.** Choose an i18n framework, then deliver Arabic/English with RTL for core flows (catalog, configurator, checkout, orders, customer portal) — a full-site RTL sweep is postponable. Add bilingual catalog content (`ProductLocalization`) and support Arabic text layers in the editor/export with correct shaping. Gate: AC #9 and I3 criteria.

**Local commerce specifics.** Wire the shop-side samples flow (fee decision pending), support vendor MOQ gating (spec-026) in checkout, and reflect local manufacturing constraints (city, capacity, lead time) in vendor profiles and PO routing.

These external steps cannot precede the entity. **Sandbox/technical integration work is not gated by this** (see §9 Payments); only live commercial activation is.

### Risks

1. **Security-regression risk on new integrations.** The Stripe/DHL webhook standard (signature verification + state re-verification + ledger) must be treated as the minimum bar for every new provider. A Paymob/Fawry integration implemented "mock-style" would recreate the exact vulnerability class SEC-03 eliminated.
2. **SEC-coupling risk on the Shipment schema change (Gate G-SHIP Branch B).** Settlements-on-delivery is SEC-03a-verified logic; under Branch B the multi-shipment change must be co-designed with the SEC track, not slipped in alongside feature work. Under Branch A the risk is deferred, not eliminated — it returns at the first genuine multi-package need.
3. **Expectation risk from broken vendor wiring.** The manufacturer portal currently demos product management that cannot work (no `/products` backend). Stakeholders should be told explicitly; fixing it is MVP item #2.
4. **Docs-vs-code drift.** `IMPLEMENTATION_STATUS.md` and `PACKHELP_FEATURES.md` overstate; future planning must cite code (this document's method), or false-confidence scope creep will recur.
5. **Market constraint if launch is Stripe-only.** USD-default Stripe-only payments exclude the dominant Egyptian payment preferences; this is the single biggest commercial blocker.
6. **Postgres 14.24 local vs production version alignment** — pin the production engine version before schema-modification waves (§6) to avoid migration drift.
7. **COD reconciliation complexity** if approved late — remittance cycles and carrier COD fees need accounting design before code. Deepened in decision #2 (§10): the selected policy (none / phone-confirmation gate / deposit + balance / hybrid) determines the payment-state and order-state model that must be designed first.
8. **`Payment.orderId @unique` — refund-path risk** (evidence: `schema.prisma:574`, `:580-581`; `stripe.service.ts:92, 123, 213-218, 354-378`; `payment.routes.ts`). The one-row-per-order design supports payment retry (intent reuse + upsert — the constraint does NOT block retries) and service-level partial refunds, but the local `refundedAt`/`refundAmount` fields are single-shot: a second refund overwrites the first (`stripe.service.ts:373-378`), and no refund API route is exposed. If FIN-04 scope grows to multi-refund/multi-attempt audit trails, the required change is a **refund-ledger entity**, not removal of the unique constraint. Classification: retry = supported; multiple sequential refunds = future risk; refund via API = currently unsupported capability.
9. **`Design.orderId @unique` — latent multi-design-ownership risk** (evidence: `schema.prisma:382, 384`; `order.service.ts:160, 217, 252-257`; `checkout.service.ts:69`; design.service.ts:506, 588-599). Multiple products and multiple distinct designs within one order are supported at the `OrderItem` level (optional, non-unique `OrderItem.designId`), and the sessionId-link cannot violate the unique because `Design.sessionId @unique` matches at most one row. The risk is latent: an order formally owns only ONE design; additional designs in the same order keep `orderId=null` and are traceable only through `OrderItem.designId`. A schema change (unique → `@@index`) becomes required **only if** formal multi-design ownership per order becomes a first-class requirement — not needed for the MVP launch path. Discovered during this pass (report-only, no doc change required): `Review.orderId @unique` (`schema.prisma:637`) = one review per order.
