## Bounded changes

Start requests lock the parent order then PO in one PostgreSQL transaction. A run already beyond not_started is returned without resetting progress/status/start/completion timestamps, rewriting the order or invoking another start notification. A new/not_started run requires confirmed PO and order vendor_confirmed or in_production, preventing terminal/earlier-state regression. Run creation/update and the applicable vendor_confirmed to in_production order write commit together. Existing authorization/ownership gates are unchanged and exercised over HTTP.

Superseded in the final stack (the earlier candidate's post-commit notification behavior no longer applies): the customer notice is now created inside the start transaction itself (NotificationService.createIfUnseenInTx in ProductionService.startProduction), checked for an existing notice by user, type and order entity under the serialized order lock, so a notice-insertion failure rolls back the whole start and a retry can complete it; a replay that observes an existing run creates no notice. Only the realtime hub publish happens after commit, and its failure is logged, not fatal, it cannot erase the persisted notice or fail the start. The helper uses a query before insertion, not a database uniqueness constraint; this is a coordinated start-path guarantee, not a guarantee against every uncoordinated notification writer. There is still no outbox or replay repair of an already-started run missing its old notice. The guarantee covers the persisted in-app notice for this start transaction, not external delivery. Returned nested order is reloaded after the transition rather than stale pre-transition data.

Production.progressPercent is an Int in the existing schema. HTTP zod and direct service now explicitly reject fractions/nonfinite/out-of-range values before persistence. No rounding or changed payment policy.

## Explicitly unresolved

This is NOT a whole production state-machine repair. The earlier candidate's completion notes are superseded in the final stack: updateProgress and completeProduction now share one transactional writer (ProductionService.writeProgress) that locks order, then PO, then the production row, rechecks the actor against the locked rows, fails 409 on a run/PO vendor mismatch, refuses changes to a closed run (quality_review/completed) or a closed parent order, and, on completion, writes quality_review, the completion timestamp and the parent order's quality_check in the same transaction and returns the state re-read inside it, so the stale100% response, nontransactional completion and closed-run mutation defects no longer apply. completeProduction has no HTTP route at this tree (HTTP completion is progress to 100 through updateProgress); its only caller found is the integration suite. What remains open about completion is the aggregate question, not the single-run mechanics: one PO completing still advances the whole order to quality_check while other POs are incomplete, the writer's own comment preserves this single-run parent effect explicitly as NOT a multi-PO projection.

Still unresolved, unchanged: QA behavior. QAService.completeQA independently writes production completed and the parent order ready_to_ship, outside any transaction or lock protocol, and no exposed caller was found for it in backend or frontend sources during this review. Sample approval still resets a production to in_progress, but in the final stack the sample writers (upload and review) run under the same order/PO/production lock ordering as the coordinated production paths (start explicitly locks order/PO; progress and sample paths additionally lock production), the review is bound to the current submission, and review is refused when the run is quality_review/completed or the parent order is closed; a same-decision retry observes the persisted review without resuming the run. Late handshake acceptance can still rewind a nonterminal parent order to vendor_confirmed (its updateMany guard excludes only terminal orders), and the handshake writer, like QA, does not take the row locks the start/progress/sample writers share. The shared lock ordering is source-grounded; it is not proof of every cross-writer interleaving. No whole-lifecycle race guarantee is claimed, and no aggregate protocol exists.

MASTER_EXECUTION_PLAN.md OPS-05 already identifies all-PO projection and partial production/shipment/delivery/cancellation as future definitions. No implemented aggregate protocol was found. Options are (A) this narrow start protection, in the final stack, with a transactional single-run completion alongside it, with aggregate completion explicitly open, (B) fail-closed multi-PO completion which could strand valid work, (C) a designed aggregate state protocol spanning PO/handshake/sample/QA. Only A is this candidate; B/C are not silently implemented. The earlier broader completion rewrite was parked; the final stack includes only the scoped transactional single-run amendment described above, not an aggregate protocol. No gateway, courier, payment-timing or additional-order policy selected. Shipment remains one shipment per whole order with placeholder weight/dimensions, and shipment creation chooses the first PO vendor as pickup origin (ShipmentService.createShipment; MASTER_EXECUTION_PLAN.md OPS-06). Do not carry forward the stale first-PO settlement claim: settleVendorForDeliveredOrder queries POs for the specified vendor, sums eligible confirmed PO costs and refuses mixed currencies; this does not close the broader settlement/refund or shipment-group operational gates. No shipment, first-PO pickup, placeholder-dimension, payment-gateway or other operational gate is decided or closed by this stack. The Egyptian payment adapters remain unavailable stubs, not implemented integrations awaiting only credentials. Checkout operator mutations remain default-off; ambiguous recovery states still require investigation. This document does not establish paid checkout-to-delivery acceptance, populated-data migration acceptance, production deployment, or physical manufacturing approval.

## Locked actor recheck amendment (v2)

No current application route/service was found that reassigns PurchaseOrder.vendorId: observed update sites set document URL, confirmed state/time, not vendor. However the foreign key is writable by an operator/direct database writer. A real disposable-DB interleaving proves such reassignment between controller authorization and the locked mutation. Start now requires authenticated actor context and rechecks its resolved vendor against the freshly locked PO before returning an existing run or creating one. ADMIN retains the existing controller vendor-profile resolution contract. A preexisting run with a vendor different from its PO fails409 for investigation, never silently transfers ownership. No vendor reassignment action is introduced. In the final stack the same locked recheck and mismatch 409 also guard the progress/completion writer (ProductionService.writeProgress), not only start.

Historical (v2 candidate): 21 HTTP/DB cases now pass. Both no-run/existing-run reassignment interleavings give403 with unchanged production/order snapshots and no notification. Removing the locked actor comparison makes both fail. An additional mismatched run/PO vendor case gives409 and ADMIN start is covered. TypeScript clean. Failed-mutant fixture cleanup now restores run ownership before deleting its synthetic vendor; the dedicated disposed database was rebuilt once after the first mutant deliberately created such a mismatched row. For the final stack's current suite counts, see Evidence above.

Qualification precision: the .int HTTP schema line is redundant with direct-service integer rejection; its independent removal does not fail the current suite, so no independent controller-line binding is claimed. Same-PO concurrency binds at least one of order/PO locks, not each separately or lock ordering against uncoordinated writers. New parent eligibility refusal follows the existing forward transition table, changes previously permissive behavior, and does not add payment verification or select a payment-release policy. The original start-notice insertion atomicity gap and the named single-run progress/completion defects are addressed within their scoped writers in the final stack (see Bounded changes and Explicitly unresolved); the handshake, QA and multi-PO aggregation items remain open as above.
