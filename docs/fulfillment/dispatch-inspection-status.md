# Read-only operator inspection checkpoint

Local default-off HTTP projection, not an operator recovery UI. No publication/deployment/activation or live carrier operation.

GET /api/consolidation/orders/:orderId/dispatch-inspection requires both CONSOLIDATION_RECEIPTS_ENABLED=true and DISPATCH_INSPECTION_ENABLED=true at request time, authenticated user, enabled manifest hub and explicit canReceive capability on that hub. ADMIN alone grants nothing. No owner/customer/vendor role bypass. The reservation's stored packet hub must match the current manifest hub. Missing manifest returns403 to avoid an existence oracle; authorized missing reservation returns404. A closed order can still be inspected because that is useful for recovery.

Projection includes prototype/read-only labels, known state/version/timestamps, conservative operator-hold flag and disposition code, no actions, payment unconfigured and dispatch disabled, attempt timestamps/state, whether a stored result exists, and a bounded paginated event-kind/timestamp ledger. Unknown stored states become unknown and request an operator hold; this is advisory and does not claim the existing writer fence enforces every unknown state. Raw result/evidence/failure codes, packet, addresses, pickup, actor IDs, provider reference, request key and hashes are excluded. Unknown event kinds become other. At most20 events, createdAt-desc, then id-desc cursor pagination; cursor contains the timestamp and id boundary. Separate pages are not a frozen audit export.

This is deliberately less than full evidence recovery: it shows presence and chronology without revealing raw provider responses or tracking references. A later authenticated adjudication design must decide what more is necessary. Hub mismatch/disabled hub/revoked capability denies inspection even for an old creator, so this is not a universal break-glass path. No new capability is granted and no separate dispatch-inspector capability is introduced; current receiver capability is the narrow established hub-bound audience.

The service imports no synthetic adapter and runs no provider lookup or command. It performs only reads inside repeatable-read transaction. GET creates no reservation, attempt, event, shipment, order change, payment or settlement. POST/PATCH/DELETE route variants do not exist. No retry-create, cancellation, refund, finalize or mark-unknown route was added. Existing post-attempt source edit/cancellation conflicts and missing operator resolution remain.

Evidence:106 local PostgreSQL prototype cases, including11 HTTP inspection cases; existing receipt HTTP23, writer25, aggregate22, receiving39, production37 pass. Types/build pass. Four guard-removal mutants fail intended assertions: capability, hub binding, dedicated gate, raw-result redaction. No browser/pixel claim, since no UI was added. Concurrency and cross-page snapshot completeness are not proven. Registered route imports add a read-only surface behind a new default-off flag, but full candidate already depends on prototype schema. Nothing is activated. Payments and dispatch remain unconfigured/disabled. Hub/global capability/directDB and legacy Stripe/DHL writer boundaries, provider integration and actual recovery/outbox/expiry remain open.

Chronology correction: descending createdAt then descending id is deterministic across tied timestamps. Matching timestamp/id predicate skips neither ties nor boundary rows in the static fixture; tests deliberately reverse lexical ID and time and split23 equal-time events across pages. Concurrent later inserts are not included in older-page cursors; this is not a frozen export. DB take bound and repeatable-read are source-present but individually unbound by mutants.
