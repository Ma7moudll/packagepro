Separate local continuation on9195e01a. Receipt correction and manifest replanning now check prototype reservation state while holding their existing parent order lock. A reserved intent is invalidated with an append-only event in the same transaction as the receiving change. Any attempt_started, reconciliation_required or label_created intent refuses that edit and requires reconciliation. Invalid input rolls back the invalidation/event. Existing idempotent receipt-event replay returns its prior result before the fence, because it makes no new correction. Confirmation remains idempotent and unchanged. No actual label, payment, settlement or notification is performed.

This modifies an existing registered receiving service to read the prototype reservation table even though the dispatch prototype itself remains unregistered. The prototype-table migration must therefore accompany any eventual publication/deploy of this service, and no deploy is approved. No runtime registration/activation, carrier request or further publication happened locally.

This is NOT every source-writer fence. Existing item/PO/design/production updates, approval reopen, generic cancellation, hub/global capability changes and direct database edits remain outside this new fence. Only packing and receiving/replan writers are now fenced. Further local engineering is unblocked, no commercial choice needed and payment remains unconfigured. The receipt-review principle is settled; the new fence protects its revision from being rewritten after a started attempt, it does not redefine who may confirm it.
