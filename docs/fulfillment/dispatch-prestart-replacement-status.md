# Explicit never-started intent replacement

Unregistered synthetic/local method only. No HTTP mutation, carrier call, production reset or live action. Existing gates and payment-unconfigured persisted inputs unchanged.

A reserved intent invalidated by a source correction formerly occupied the unique order reservation forever. replaceBeforeStart now permits explicit replacement only for invalidated_before_start or cancelled_before_start, with expected current version, same original creator and different request key. It refuses any attempt-history row even if a directDB/operator has made the reservation state misleading. It locks the order, rebuilds the server packet using current manifest hub, fresh team confirmation and input/payment/authority checks, updates intent version and appends an event with prior/current hashes and prior version/state. No old event is changed. It does not itself claim or execute. A later explicit synthetic execution is a separate operation.

Repeated replacement is not an automatic retry and stale versions fail. Two concurrent replacements permit one version winner. Already reserved, started, unknown and labeled attempts cannot be reset, and no lookup result is treated as proof that a previous create did not happen. There is no order cancellation, payment, refund, settlement or real Shipment write. Same request key does not silently replay a replacement. The previous request key is not preserved in event evidence, while its packet hash/version/state are. No permanent globally unique request-key journal is introduced.

Evidence:118 disposable PostgreSQL cases pass, including actor/capability/current-review/new-key/version, all post-start refusal states, inconsistent pre-start state with durable attempt, two-replacement concurrency, sandbox/payment/authority, server-packet refresh and append-only replacement evidence. Four mutants fail intended assertions: attempt-history guard, creator binding (using a second authorized receiver), replacement event, current packet/payment recheck. An initial creator-removal mutant survived when other missing capability/stale-review barriers masked it; added a focused authorized-receiver case, then it fails. Sources restored. Backend types/build pass. No broad race/deadlock guarantee or individual lock proof.

No application hub/capability mutation writer was found, so no new administrative account-change API was invented. DirectDB/operator writer gaps remain. No authenticated post-attempt adjudication or recovery mutation endpoint exists. Inspection still maps the new replacement event to other until a deliberate DTO allowlist change; raw event evidence stays private. Full candidate remains coupled to prototype schema and is not runtime-isolated. No publication/deployment/activation authorized.

Contract addendum:121PG now includes isolated stale-version, live-reserved and same-key refusal cases. Early version-check removal survives because conditional update remains a barrier; this is explicitly redundant/unbound. Reserved-state and same-key mutants fail. No source change.
