# Local writer-guard proposal

Review only. Based on aggregate observation tree 08caf3cfee3e0670f49c7ae98cc5b2d870d0c761. No publication, integration, migration, merge, deployment or operational activation requested by this patch.

## Changes

- A production run reaching 100% remains per-run completion. Parent quality_check requires every PO to be confirmed with matching-vendor production at 100% and quality_review/completed. Existing earlier parent stages only may advance. A later parent stage cannot regress. The parent row serializes cooperating completions, and PO/production rows are locked for the aggregate read.
- Legacy completeQA still completes one run. It no longer writes parent ready_to_ship. Its checklist/reviewer return is not durable QA evidence; no callers/routes were found. This is containment, not a new QA model.
- Generic admin/internal order transitions reject quality_check, ready_to_ship and shipped with 409. No endpoint was added to replace those transitions.
- Handshake acceptance still confirms its PO and retains the delivered-settlement helper. Its parent transition only accepts ready_for_routing. Parent lock is taken before the PO write to match production/receipt lock order, avoiding a new opposite-order cycle with production's aggregate PO locks.

## Customer and operations consequences

- The first of multiple factories finishing no longer places the whole order into quality_check or prevents another run starting solely for that reason. The final qualifying completion puts it into quality_check, not dispatch readiness.
- Generic ready/shipped actions now fail, including administrative ones. No override or commercial exception is introduced.
- The existing manufacturer order-detail UI has an optimistic ready_to_ship setter before its generic request and no local catch/rollback in that handler. Its completed-run mapping also uses ready_to_ship. Those UI controls were NOT changed in this backend-only proposal. This patch must not be activated as a complete customer-facing workflow; that UI would misrepresent the rejected state until refreshed. A follow-on UI change must remove the unsupported action and distinguish factory completion from whole-order shipping, then receive browser verification.
- Existing persisted ready_to_ship orders can still enter the legacy shipment service. That path still has separate carrier, pickup, measurement and atomic-recheck issues. This patch does not close it and makes no shipping-safety claim.
- No new customer notifications, payment release policy, durable QA approval, dispatch authorization or carrier activation. Existing production-start notices and delivered settlement behavior remain.

## Targeted semantic/lock closure

Added a separate finished-at99 other run case, plus three transaction barriers against direct Prisma writers that do not take the parent lock. The barriers pause immediately before the protected aggregate read (PO and production), or before handshake mutation after its parent lock, and require a real PostgreSQL Lock wait to be observed before releasing the service transaction. Direct writes complete after commit. Removing each of the three specific locks fails its own barrier assertion; removing the exact100 predicate incorrectly advances the parent and fails its assertion. These four targeted mutants supplement, rather than replace, the earlier four baseline-file mutants.

Locks guarantee stability only during this transaction. A nonparticipating writer can change a PO or run immediately after commit, leaving the parent quality_check stale. No durable eligibility, future writer discipline or dispatch authority follows from these tests. Any release consumer must revalidate under its own atomic reservation boundary.

## Manufacturer list response mismatch closure

The actual vendor controller returns purchaseOrder.findMany with the full parent order relation (and items), so normal responses carry two different status fields. PurchaseOrder.status is an unconstrained Prisma String, not the parent lifecycle enum. The frontend contract separately makes order and order.status optional. Therefore a confirmed PO with an in-production parent is normal, and a legacy ready PO beside another/missing parent status must not suppress its warning.

Manufacturer list warning now appears if either displayed PO status or parent status is ready_to_ship. It does not overwrite either status. Four EN/AR fixture cases cover PO ready with parent in_production or omitted; all pass, and inspected320px screenshots show the warning beside the badge. Restoring the former parent-first fallback fails the mismatched-parent assertion. Exact affected case passes after restoration; frontend typecheck passes. This remains UI-fixture/contract inspection, not a live provider response test.
